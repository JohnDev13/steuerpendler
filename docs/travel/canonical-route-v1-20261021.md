# Canonical Route v1 — contract, not generated results

**Design date:** 2026-10-21. **Status:** definition ready for implementation; no `Route` records or all-19 result file have been generated. This document and `canonical-route-v1.schema.json` define the authoritative *route-time* artifact. `SPEC.md` remains the governing product policy; its §6/§8 amendment points here. Historical source `docs/source/SPEC-v1.1-2026-10-17.md` stays unchanged.

## What one Route means

A `Route` record is the **fastest-route search result for one exact first-boarding event to one selected workplace capital**, on the owner-approved **2026-10-27** service day. It contains a feasible itinerary only when one has been evidenced; its status distinguishes a proven fastest route from a provisional best-found or unknown result. The event is `(GTFS trip_id, expanded trip-instance ID, child stop_id, stop_sequence, departure seconds since GTFS service midnight)` at a boardable child stop mapped to one of the **2,110 residential tax BFS municipalities**; the destination is its workplace **BFS ID** and one of that workplace's source-checked terminal children. This is **not** a municipality-centre, door-to-door, station-name, or capital-to-capital route. The primary key is `(origin.tripInstanceId, origin.stopId, origin.stopSequence, origin.boardSeconds, destinationBfs)`; all 19 destinations must be considered for each eligible boardable first event. No duplicate keys.

Only first departures within **06:30:00–08:30:00 Europe/Zurich inclusive** qualify. Departures and arrivals retain exact GTFS service-day seconds, including values beyond 24:00:00. `elapsedSeconds = finalArrivalSeconds − firstBoardSeconds` includes on-vehicle time, interchanges, transfer walking/minima and waiting **after** the first boarding; it excludes waiting before first boarding. `minutes = ceil(elapsedSeconds / 60)` is for display and slider comparison only. Select the minimum **unrounded** elapsed seconds before ceiling, within **1,800 seconds**; equal elapsed paths tie-break by fewer transfers and then stable lexicographic trip-instance/stop/sequence IDs. A path at 1,800 seconds qualifies; one at 1,801 does not. No circular radius or departure-frequency percentile.

Each itinerary stores ordered trip legs (source trip/instance, route/service, child boarding/alighting IDs, sequences, exact event seconds) and one **directed evidenced transition** between successive legs (endpoint IDs, arrival/departure, minimum seconds, source rule). Transfer wait and minimum are not added again to elapsed time. Continuing on the same trip is one leg. Do not assume that two trip IDs imply two vehicles. Respect dated calendar exceptions, pickup/drop-off, whole-trip chronology, parent/child specificity, forbidden/time-specific rules, and frequency semantics. `exact_times=0` is not a fabricated fixed departure; unresolved type-1/type-4/service-specific transfers do not become zero-minute walks. The documented Swiss **120-second same-parent fallback** is an interchange minimum, never an extra entrance-to-platform access penalty. Cross-station interchange needs actual evidence, not a shared name.

## Single source-of-truth file

The **only authoritative generated route-time file** is `data/travel/canonical-routes-v1-20261027.ndjson.gz` (outside public Git until genuinely built and reviewed). Deterministic UTF-8 NDJSON records in a gzip stream (`mtime=0`, no original filename): exactly one `kind:"manifest"` first line, one `kind:"route"` record per expected event×destination pair sorted by numeric destination BFS then event `(boardSeconds, stopId, tripInstanceId, stopSequence)`, and one `kind:"summary"` last line. Each route line validates against `canonical-route-v1.schema.json`. There is no second manually maintained minutes table. Public `site/data/travel/to/<bfs>.json` and any Gemeinde views are derived from this exact file, with its external SHA-256 recorded in the deterministic site release manifest.

The manifest identifies schema version, date/timezone, the inclusive window and cap in exact seconds, sorted **19** workplace IDs and verified child terminal groups, GTFS/feed and target-candidate SHA-256, source service/stop coverage, municipality boundary/ID vintage, generator commit, access model and minute rounding. The summary records exact expected/emitted event×destination pair counts, unique-key and status counts, unresolved classes, source scan counts, and whether all events and timetable/transfer classes were searched. Record the output SHA-256 in the **separate** deterministic release manifest, not in the hashed file itself. Freeze generator/source versions; do not embed run timestamps or a self-referential digest. Fail on mismatched input hashes, malformed source rows, duplicates, missing pair counts, or non-deterministic rebuild.

One pair has **exactly one** status:
- `fastest_proven`: an evidenced itinerary within 1,800 seconds and a complete search proving no faster competing itinerary; `itinerary` present, `unresolvedReasons` empty.
- `best_found_unproven`: an evidenced feasible itinerary, but an unresolved source/search class might be faster; keep its exact upper-bound time, mark the estimate provisional, **never label it “the fastest.”**
- `unreachable_proven`: complete source/transfer/endpoint search proves no itinerary within 1,800 seconds; `itinerary:null`. This is a negative claim only about this particular boarding event.
- `unknown`: no evidenced feasible itinerary and incomplete relevant evidence; `itinerary:null`, reasons nonempty. Unknown is not a 0-minute or unreachable route.

`best_found_unproven` and `unknown` carry nonempty machine-readable reasons; only proven states have empty reasons. The JSON Schema enforces shape; a streaming semantic validator must additionally enforce timestamp arithmetic, the 30-minute cap, first/last leg identity, leg chronology, transfer count/clock/minimum and provenance, terminal membership, day/service activity, deduplication and whole-file pair coverage. Structural schema success alone cannot establish optimality or GTFS truth.

## Municipality projection and current approximation

All **2,110 residential Gemeinden** stay in the downstream origin universe; the 19 workplaces are only destinations. A separate versioned stop→Gemeinde mapping determines which *actual child boarding stops* can stand for a residence. For the owner's current indicative policy, label external residential-to-entrance access `zero_unmeasured_provisional`, with zero **assumed** access seconds; **do not** assert a measured walk, infer cross-border hubs from zero, or add entrance-to-platform walking. The walking slider remains a separate UI control, but its zero-assumption mode must be visibly labelled as not measuring a walk. No local boarding stop or no proven event is a **coverage/no-evidence** state, not proof that the Gemeinde lies outside 30 minutes. Preserve non-capital and neighbouring-canton origins; do not turn this file into a capitals×capitals matrix.

For a Gemeinde→workplace result, compare its permitted board events/routes using exact transit seconds, and retain necessary alternatives if a later measured-walk mode is enabled. The defined same-Gemeinde workplace identity case with zero transit is a policy sentinel, **not** a fabricated scheduled Route record or a second time table. A route whose status is `best_found_unproven` may be shown **only as an indicative best found**; it cannot support a fastest-route guarantee or an exclusion. Do not publish a negative Gemeinde classification unless the origin-access model and all relevant board events have complete coverage. The user's acceptance of the prior SBB material is recorded as **owner acceptance**, not a new independent 30-case replay. Tax accuracy/quarantine and content/rights approvals are separate from this route-time definition.
